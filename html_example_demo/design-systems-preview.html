Streaming ingestion pipeline

A design note on how events move from the edge collectors into the warm store, why the buffer sits where it does, and what happens when a partition falls behind.

Updated 14 March · 9 min read · owned by Platform Data

Why a buffer at all

Collectors emit at wildly uneven rates. A single deploy can push a region from 2k events/sec to well past forty thousand for a couple of minutes, and the warm store's write path is not elastic on that timescale. The buffer exists to absorb that shape so the store only ever sees a smoothed curve.

Everything downstream assumes at-least-once delivery. Deduplication happens at read time using the event_id + ingested_at pair, which means a replay is always safe — a useful property when a consumer group needs to be rewound after a bad release.

If you find yourself reasoning about exactly-once semantics here, you have taken a wrong turn. The contract is at-least-once, and the reader is idempotent.

Partition assignment

Partitions are keyed by tenant, not by collector. This keeps a noisy tenant's backlog contained inside its own partition instead of spreading lag across every consumer in the group.

  • Tenant key — stable, so ordering per tenant is preserved across rebalances.
  • Collector key — rejected; collectors churn during rollouts and every churn triggers a rebalance.
  • Round robin — rejected; no ordering guarantee, and the reader depends on it.
consumer.ts// Lag is measured per partition, not per group — a single hot tenant
// should not make the whole group look unhealthy.
export async function pollBatch(
  partition: Partition,
  budgetMs = 250
): Promise<Batch> {
  const deadline = Date.now() + budgetMs;
  const events = [];

  while (Date.now() < deadline) {
    const record = await partition.next();
    if (!record) break;
    events.push(record);
  }

  return { partition: partition.id, events, source: "warm" };
}

Backpressure thresholds

The writer sheds load in stages rather than failing outright. Each stage is observable, so an on-call engineer can tell which stage is active from a single dashboard row.

StageTriggerEffect
Normallag < 30sFull fidelity, all fields written
Trimlag 30–120sOptional payload fields dropped
Samplelag 2–10 min1-in-4 sampling on debug-level events
Divertlag > 10 minOverflow written to cold object storage
Note

Diverted batches are replayable but not queryable until the backfill job runs. Expect a gap in the warm store for the duration.

Warning

Never lower divert_threshold below the backfill job's typical runtime. Doing so produces overlapping backfills that compete for the same write budget.

Open questions

  1. Should the sampling stage be tenant-configurable, or is a global rate simpler to reason about?
  2. Does the cold-storage divert need its own retention policy, or does it inherit the warm store's?

One spacing & sizing scale, four themes

Cursor's scale is now the shared geometry for every theme — ErgoRead, Executive, and the two that already shipped (Claude and GitHub). Only colour and the heading scale differ between them now. This is applied in the extension itself, not just this preview: media/theme.css holds the tokens, media/claude-markdown.css consumes the prose ones, media/claude-base.css consumes the chrome ones.

Cursor splits its scale in two, and that split is worth copying: fixed px for UI chrome (toolbars, panels, badges stay aligned regardless of reader font size) and em-relative for prose (paragraph rhythm scales with the text). The old chrome values — 12 / 16 / 24px — landed exactly on Cursor's grid, so that migration was lossless.

Two places I deliberately diverged from Cursor. Its headings are font-size: inherit with flat 0.5em margins — correct for a chat transcript, wrong for a document with real structure, so headings keep a size scale and get 1em above / 0.5em below, which groups a heading with the text it introduces. And its list items inherited a 1.4 code line-height in our CSS; prose list items now use --leading-body.

Cursor teardown — measured, not guessed

Cursor is installed on this machine, so these numbers come from reading its own stylesheet (resources/app/out/vs/workbench/workbench.desktop.main.css) and its bundled theme (extensions/theme-cursor/themes/) directly, then running the hexes through OKLCH and APCA.

1. The surfaces are pure grey — chroma exactly 0.000

Cursor Dark's canvas is #181818 and its foreground #F0F0F0. Both measure C = 0.000. Cursor Light is #FCFCFC / #141414 — also 0.000. There is no tint anywhere in the reading surface. This is the single biggest reason it feels calm, and it is the opposite of what the first draft did.

2. One colour, derived ~40 ways by alpha

Cursor barely defines a palette. It defines a foreground and derives everything else from it with color-mix(… , transparent). Nothing can clash because there is only ever one hue in play. The exact ladder, resolved over #181818:

3. Prose text is deliberately dimmer than code

This is the detail that matters most, and it is easy to miss. Editor text runs at full strength, Lc −96.9. But rendered prose uses hsla(0,0%,89%,.92), which resolves to #D3D3D3 — Lc −78.8. Cursor steps prose down roughly 18 Lc from its code. That lands almost exactly on the 75–88 reading band, and almost exactly where this rebuild independently landed (−76.3).

5. Its accents are Nord

Cursor Dark's link colour is #81A1C1 and its cyan is #88C0D0 — those are nord9 and nord8 verbatim. Measured chroma 0.059 and 0.062, i.e. very desaturated. That is the same conclusion this rebuild reached from a different direction, which is a good sign.

One thing I did not copy: Cursor's links sit at Lc −48.5, which is genuinely faint for prose. The Cursor palette here keeps its hues but lifts link lightness to Lc −63.

What changed, and why

The first pass was Catppuccin-derived, and that is exactly what made it feel intense. Measured in OKLCH, its canvas carried chroma 0.030 and its body text chroma 0.043 — both at hue ~275–285. So the surface and the text were tinted the same violet, and there was no neutral anywhere for your eye to settle on. Prevailing guidance for dark UI is a canvas tint of about 0.01; this was three times that. The links compounded it at chroma 0.111.

The rule this rebuild follows: surfaces stay near-neutral, accents carry all the colour. That is why Gruvbox (canvas chroma 0.000) and GitHub dark-dimmed (0.015) read as calm while Catppuccin and Tokyo Night read as vivid.
